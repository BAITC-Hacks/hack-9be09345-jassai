# Career Quest — ИИ-навигатор развития сотрудника

Проект команды **JassAI** для **HackAlem AI**, трек **Halyk Bank**, кейс 1.

Career Quest помогает сотруднику понять, какие активности приближают его к карьерной цели, а HR — увидеть дефициты компетенций и пробелы в доступных программах развития.

> **Статус: проектирование и подготовка разработки.** Этот коммит фиксирует концепцию, обязательные требования, архитектуру и план команды. Код приложения, launcher и интеграция с AI ещё не реализованы. Описанные ниже возможности — целевой объём разработки, а не уже работающие функции.

## Проблема

Обучение, аттестации, менторство и другие HR-события приходят сотруднику разрозненно. Связь между конкретной активностью и профессиональным ростом неочевидна. Career Quest должен объединить профиль, историю участия и требования карьерной цели в понятную траекторию с объяснимым следующим шагом.

Основной пользователь — сотрудник со стажем 1–5 лет. Второй пользователь — HR-специалист.

## Основной сценарий

1. Сотрудник входит в приложение и видит профиль, навыки, историю и карьерную цель.
2. Система определяет разрывы между актуальными навыками и требованиями целевой роли/грейда.
3. AI предлагает 1–3 допустимые активности и объясняет выбор минимум по трём факторам.
4. Сотрудник выполняет активность и отмечает её завершение.
5. Программа обновляет навыки и траекторию по правилам датасета, сохраняет результат и актуализирует рекомендации.
6. HR видит дефициты навыков, участие в мероприятиях и сотрудников, для которых нет подходящего следующего шага.

## Обязательные функции

| Функция | Что должно работать |
|---|---|
| Профиль и траектория | Роль, грейд, навыки, история, карьерная цель и разрывы до неё |
| AI-рекомендации | 1–3 релевантных мероприятия с учётом нескольких факторов |
| Объяснение выбора | Не менее трёх факторов: цель/грейд, дефициты навыков, критические требования, история участия |
| Обновление прогресса | Корректное применение `gain` и `max_level`, сохранение результата, защита от повторного начисления |
| HR-view | Дефициты компетенций, отсутствие подходящего шага с причиной, участие по мероприятиям |
| Импорт жюри | Загрузка дополнительных профилей и истории в формате датасета без изменения кода |
| Разграничение доступа | Сотрудник видит собственные данные; HR получает разрешённый обзор |
| Воспроизводимость | Запуск через launcher и документированный проверочный сценарий |

## Формат приложения и запуск

Целевой формат — **локальное веб-приложение для Windows 10/11 x64**. Пользователь скачивает приватный репозиторий, распаковывает архив и запускает `launcher.cmd`. Приложение открывается в браузере и работает на локальном компьютере.

Планируемое поведение launcher:

- автоматически подготовить Python и закреплённые зависимости в изолированном окружении;
- запустить локальный сервер на `127.0.0.1` и проверить его готовность;
- открыть браузер с мастером первоначальной настройки;
- предложить загрузить предоставленный организаторами датасет и указать действующий API-ключ;
- сохранять БД и настройки между запусками;
- показывать понятную диагностику при ошибке установки, запуска или доступа к API.

Ручная установка Python, Node.js, Docker и отдельной БД пользователю не планируется. Первый запуск потребует интернета для зависимостей. Облачные AI-рекомендации потребуют доступного API и ключа с необходимыми правами и кредитами. Без AI-доступа ограниченный режим будет явно обозначен.

**Сейчас запустить приложение нельзя:** launcher и исходный код появятся в следующих коммитах. Точные команды запуска, требования к окружению и инструкции проверки будут добавляться по мере реализации и фактического тестирования.

## Планируемые технологии и архитектура

| Компонент | Выбранный подход |
|---|---|
| Сервер и API | Python, FastAPI |
| Интерфейс | HTML, CSS, JavaScript; ресурсы обслуживает тот же сервер |
| Хранение | SQLite |
| AI | Адаптер разрешённого облачного LLM API; модель будет указана после проверки доступа |
| Окружение и зависимости | uv, закреплённые версии и lock-файл |
| Запуск | `launcher.cmd` и вспомогательный PowerShell-скрипт |

```text
Launcher → локальный сервер → браузер
                  │
                  ├── импорт и проверка данных
                  ├── SQLite: профили, история, настройки
                  ├── расчёт навыков и доступности мероприятий
                  ├── AI: выбор и объяснение следующего шага
                  └── HR-аналитика
```

Сервер рассчитывает навыки, разрывы и допустимость мероприятий. LLM выбирает и ранжирует подходящие шаги с учётом контекста и объясняет решение. Ответ модели проверяется: она не должна придумывать мероприятия или самостоятельно определять числовой прирост навыков.

## Данные и правила

Используется синтетический стартовый набор Career Quest, предоставленный организаторами:

| Файл | Содержание |
|---|---|
| `employees.json` | 200 профилей сотрудников |
| `events.json` | 40 мероприятий |
| `skills.json` | 60 навыков и требования для 8 ролей × 4 грейдов |
| `activity_history.csv` | 24 месяца истории; 2 743 записи по README датасета |

Размер стартового набора не ограничивает количество импортируемых профилей жюри. Исходные данные и секреты не включены в этот коммит.

Ключевые правила реализации:

- Дата среза — **2026-10-01**; она используется как «сегодня» в демонстрации.
- Отсутствующий навык считается равным нулю.
- Профиль содержит навыки на дату последней оценки. Завершённые активности после `last_review_date` нужно учитывать дополнительно, без двойного начисления.
- Прирост ограничивается `gain`, `max_level` и общей шкалой 0–5. Уже достигнутый уровень не уменьшается.
- Обязательные мероприятия исключаются из рекомендаций добровольного развития.
- Учитываются текущая роль и грейд, prerequisites, даты сессий и история завершений.
- Завершённое мероприятие не назначается повторно, кроме регулярного клуба `EV_036`.
- Цель может отсутствовать или предполагать смену роли; эти случаи должны обрабатываться явно.
- Если подходящих мероприятий нет, система показывает причину, а не выдумывает рекомендацию.

Источник конкретных схем и семантики полей — README выданного датасета.

## План на 5 часов

Команда состоит из трёх человек. Направления ответственности: **A — сервер и данные**, **B — AI и launcher**, **C — интерфейс и документация**. Каждый участник документирует и проверяет свою часть.

| Час | Планируемый результат |
|---|---|
| 1 | Launcher, каркас приложения, импорт набора, профиль; проверка реального доступа к модели |
| 2 | AI-рекомендации, объяснения по нескольким факторам, серверное разграничение ролей |
| 3 | Импорт профилей жюри, завершение активности, пересчёт и сохранение прогресса |
| 4 | HR-view, граничные случаи, проверки корректности, актуальный README |
| 5 | Запуск из чистой копии на втором компьютере, исправления, демонстрация и сдача |

В конце каждого часа команда выполняет содержательный commit и push с фактическим результатом. После четвёртого часа новые функции не добавляются: остаются проверка, исправления и подготовка сдачи.

Это план, а не отчёт о завершённых этапах. Текущий коммит содержит только README.

## Как будет проверяться решение

Проверочный сценарий для будущей реализации:

1. Скачать и распаковать репозиторий на втором компьютере, выполнить запуск через launcher.
2. Пройти настройку и импортировать разрешённый датасет.
3. Загрузить новый профиль сотрудника и дополнительную историю в формате стартового набора.
4. Получить AI-рекомендацию и проверить её допустимость и минимум три фактора объяснения.
5. Завершить мероприятие, проверить точный прирост навыков и изменение траектории.
6. Повторить запрос завершения: дополнительное начисление недопустимо.
7. Перезапустить приложение и проверить сохранность результата.
8. Открыть HR-view и проверить три обязательных среза.
9. Проверить запрет доступа сотрудника к чужим данным и HR-операциям.

Дополнительные ситуации: повторные пропуски, критический навык вместо минимального, потолок навыка, невыполненный prerequisite, отсутствие цели, Lead, смена роли, повторяемый клуб, отсутствие кандидатов и недоступность AI API.

Целевые задержки по ТЗ компании: отклик интерфейса до **2 секунд**, AI-рекомендация до **10 секунд**. Установка окружения измеряется отдельно. Результаты тестов и замеров пока отсутствуют; они будут опубликованы после реализации. Нагрузочное тестирование без разрешения организаторов не проводится.

## Безопасность и ограничения

- Доступ к репозиторию ограничивается командой и организаторами.
- API-ключи, пароли и токены не размещаются в коде, истории Git, чатах, презентациях и логах.
- Используются только разрешённые данные и сервисы; реальные персональные и производственные данные не требуются.
- Сервис работает локально; публикация в интернет и локальную сеть не включается автоматически.
- Ограничения устройства и сети не обходятся; средства защиты не отключаются.
- Данные вовлечённости других сотрудников не показываются сотруднику.
- Покрытие требований по навыкам не означает автоматическое повышение грейда.
- Локальный прототип не заявляется готовой корпоративной системой: центральный сервер, SSO и промышленная инфраструктура находятся за рамками пяти часов.

Геймификация, внутренняя валюта, магазин наград, календарь и прогноз оттока не входят в обязательный объём. Публичные рейтинги эффективности сотрудников и поощрения за обязательные процессы не реализуются по условиям кейса.

## Ценность и развитие

Основная гипотеза: объяснимая связь между мероприятием и карьерной целью помогает сотруднику выбирать полезные добровольные активности. HR получает основания для изменения каталога обучения, когда подходящего шага нет.

В дальнейшем эффект следует проверять в пилоте: принятие рекомендаций, завершение добровольных активностей, явка и обратная связь о полезности объяснений. Синтетический датасет сам по себе не доказывает рост вовлечённости или экономию бюджета.
